# Infrastructure

Terraform for Pitman's production stack at `pitman.jaredhoward.com`, in
Pitman's own AWS account. **How to deploy it (the operator's numbered
first-deploy runbook), the CI variables, the Lambda environment and what
IC-WBT must grant: `docs/deployment.md`.** This file is the map of the code.

## What it creates

| File | Resources |
|---|---|
| `main.tf` | Providers: primary `aws_region` (`af-south-1`, D-6) and `aws.us_east_1` (CloudFront's certificate, WAF and metrics); partial S3 backend (bucket and region from `backend.config`) |
| `s3_cloudfront.tf` | Private site bucket (`pitman-frontend-<account>`, OAC-only, TLS-only); ACM certificate (us-east-1) validated in the delegated child zone, which is **looked up** (`data.aws_route53_zone`), never created; CloudFront with two behaviours: default → S3 (`functions/spa_rewrite.js`), `/api/*` → Lambda Function URL (`functions/api_strip_prefix.js`, signed by the `lambda` OAC `pitman-api-oac`, shared-secret header as the second lock, caching off, 30 s read timeout); CloudFront's two invoke permissions on the function (`lambda:InvokeFunctionUrl` and `lambda:InvokeFunction`, `source_arn` = this distribution; #33, R4-I6); A + AAAA alias records |
| `security_headers.tf` + `csp.json` | Response-headers policies: the site's strict CSP (split with SvelteKit's meta-tag hash; the reasoning is in the file), HSTS, nosniff, DENY framing, COOP, Permissions-Policy; the API's `default-src 'none'` |
| `waf.tf` | WAFv2 web ACL (us-east-1): per-IP rate limits on `/api/auth/*` except `/api/auth/me` (100 / 5 min, evaluated first), `/api/*` (300 / 5 min) and every path (2 000 / 5 min); paths are URL-decoded, backslash-folded and normalised (`NORMALIZE_PATH_WIN`) and lower-cased before matching; sampled requests off (they would keep the session cookie and IPs in us-east-1), metrics on |
| `lambda.tf` | API Lambda (Node 24, arm64, 1 024 MB (1 024-2 048), 30 s, reserved concurrency 10 (5-10, at least 5 for the two SQS triggers; concurrency × memory at most 10 GB); the function owns `reserved_concurrent_executions`, so an apply undoes a breaker trip), its log group (30 days; JSON log format with platform logs at `WARN`, so no START/END/REPORT lines, and application logs at `INFO`, which keeps every line the backend writes), its role (own log group only, plus the cross-account read of IC-WBT's `rnl/*` and MAP-grid file, each conditioned on IC-WBT's account and present only once configured), its environment (incl. the sign-in variables, `MAIL_QUEUE=sqs` with the mail queue's URL, `USAGE_STORE=dynamodb` with `USAGE_TABLE`, the Cape Farm Mapper variables from `cfm_token` (sensitive) and the layer URLs, and `DATA_REGION` = `icwbt_region`, `docs/deployment.md` § Lambda environment), the `AWS_IAM` Function URL (only CloudFront's OAC-signed requests invoke it; `docs/deployment.md` § Lambda origin access control) |
| `breaker.tf` + `functions/breaker/` | The spend circuit breaker (R4-I7): SNS topic `pitman-breaker` (only CloudWatch, for this account, may publish) → Lambda `pitman-breaker` (plain JS, Node 24, arm64, 128 MB, 10 s, reserved concurrency 1, logs 30 days), whose role may only `lambda:PutFunctionConcurrency` on `pitman-backend` and write its own log group. Two trips, each also mailing `alerts`: `pitman-breaker-api-concurrency` (`ConcurrentExecutions` Maximum ≥ `breaker_concurrency_threshold`, 6, in 3 of 3 five-minute periods) and `pitman-breaker-api-duration` (`Duration` Sum over an hour > `breaker_duration_ms_per_hour`, 7 200 000 ms, 2 copies busy all hour). `pitman-breaker-errors` mails if the breaker itself fails. Reset: `terraform apply` (or `docs/security.md` § Incident playbook) |
| `usage.tf` | The usage table `pitman-usage` for the per-user daily quotas (R4-I9, R4-D7): on-demand capped at 5 read / 10 write units a second, hash key `pk` (S), TTL on `expires_at`, AWS-owned key, no PITR. Grants the Lambda `dynamodb:UpdateItem` on it only. Alarm `pitman-usage-table-throttles` |
| `users.tf` | The user table `pitman-users` (DynamoDB on-demand capped at 50 read / 10 write request units a second, sized from auth-kit's per-request reads and transactions, `pk`/`sk`, TTL on `ttl`, PITR, deletion protection, AWS-owned key; A-AUTH-4). Grants the Lambda exactly auth-kit's six actions (`GetItem`, `Query`, `PutItem`, `UpdateItem`, `DeleteItem`, `ConditionCheckItem`) on the table ARN only: no `Scan`, no `Batch*`, no index ARN. The two sign-in keys (`random_password.auth_code_key`, `random_password.auth_session_key`; A-AUTH-8) |
| `ses.tf` | SES v2 sender (A-AUTH-7): identity `pitman.jaredhoward.com` with Easy DKIM (3 CNAMEs, af-south-1's regional DKIM domain), MAIL FROM `send.<domain>` (MX + SPF), DMARC `p=none` on `_dmarc.<domain>`; configuration set `pitman` (TLS required, suppression of bounces and complaints, reputation metrics; no per-event CloudWatch destination, which would cost ~$2/month with no alarm on it). Grants the Lambda `ses:SendEmail` on the identity and the configuration set only, when From is `no-reply@<domain>`; never `ses:DeleteSuppressedDestination`. Bounces and complaints: SNS `pitman-ses-events` (only this configuration set may publish) → SQS `pitman-mail-events` (only that topic may send; SSE; DLQ after 5 tries) → an event source mapping on the same API Lambda (batch 10, 5 s batching window, at most 2 at once, `ReportBatchItemFailures`; queue visibility = 6 × the Lambda timeout + the batching window). The handler logs each event; flagging the address on the Users page comes with auth-kit v0.2.0, which may only receive, delete and read attributes on that queue |
| `mail_queue.tf` | The sign-in mail queue (issue #30, A-AUTH-14): SQS `pitman-mail-send` (SSE-SQS; retention 10 minutes, a code's life; visibility 6 × the Lambda timeout; DLQ `pitman-mail-send-dlq` after 3 receives, kept a day) with a queue policy that only refuses non-TLS requests. `POST /auth/code` enqueues one sealed message per accepted request (a decoy for an unlisted address) and the same API Lambda consumes it through an event source mapping (batch 10, no batching window, at most 2 at once, `ReportBatchItemFailures`). Grants the Lambda `sqs:SendMessage`, `ReceiveMessage`, `DeleteMessage` and `GetQueueAttributes` on that queue only |
| `alarms.tf` | Monthly budget (gross: credits and refunds excluded; forecasted 100 %, actual 80 % and 100 %; `budget_monthly_usd = 0` only with `no_budget_acknowledged = true`); SNS topics in both regions (alarms can only notify a topic in their own region); alarms on Lambda errors, throttles, invocations (`lambda_invocations_alarm_per_hour`, 2 000) and p95 duration, CloudFront requests and bytes (`cloudfront_requests_alarm_per_hour`, default 20 000; `cloudfront_gb_alarm_per_hour`, default 1 GB), Route 53 queries on the zone (`route53_queries_alarm_per_hour`, 20 000, us-east-1), each of those four a 5-minute sum against a twelfth of its per-hour variable, CloudFront 5xx, WAF blocks (all rules, and the auth rule alone), SES bounce and complaint rates, user-table throttles and system errors, the `auth.locked`, `mail.send_failed`, `auth.unconfigured` (each ≥ 1 in 5 min) `auth.send_capped` (≥ 1 in 15 min), `auth.slow_code_request` (≥ 3 in 15 min), `cloudfront_secret.unset` and `mail.events_unrecorded` or `mail.queue_unsent` (≥ 1 in 5 min), `mail.enqueue_failed` and `mail.send_expired` or `mail.queue_unreadable` (each ≥ 1 in 5 min), `mail.record_failed` (≥ 3 in 15 min) and `mail.event_refused` or `mail.event_ignored` (one filter, `?"…" ?"…"`; ≥ 1 in 1 h: a bounce or complaint dropped unrecorded, likely a change in SES's event shape or timestamps) log lines, the mail-events and mail-send DLQs, and the age of the oldest sign-in email on `pitman-mail-send` (over 2 minutes). WAF alarms take their `WebACL` and `Rule` dimensions from the ACL's metric names |
| `oidc.tf` | Looks up the bootstrap's `pitman-deploy` role and attaches the deploy policy: sync the site bucket, invalidate this distribution, update this function's code (`UpdateFunctionCode`, `GetFunctionConfiguration`; no `GetFunction`). Nothing else: it can't change the concurrency or undo a breaker trip |
| `outputs.tf` | What `export-tf-vars.sh` pushes to repo variables, plus `lambda_role_arn` for IC-WBT's bucket policies |

Created elsewhere, by the estate bootstrap (`~/github/templates/scripts/new-project-account.sh pitman`): the account, the tfstate bucket, `alias/pitman-sops`, the GitHub OIDC provider and deploy role (trust pinned to `repo:Absence0760@21693150/pitman@1437736870:environment:production`: this repo uses GitHub's immutable subject claims, owner and repo each followed by its numeric ID; check with `gh api repos/Absence0760/pitman/actions/oidc/customization/sub --jq .sub_claim_prefix`, project-mgmt Runbook G), the `pitman.jaredhoward.com` zone and its delegation. The `production` environment (you as required reviewer) comes from `~/github/templates/scripts/backfill-prod-environment.sh --apply Absence0760/pitman`, run once the repo is public (required reviewers need a public repo on GitHub Free); `docs/deployment.md` § First deploy has the order.

## Checks (credential-free)

- `terraform fmt -check -recursive infra && terraform -chdir=infra init -backend=false && terraform -chdir=infra validate`: also CI (`terraform.yml`).
- `terraform -chdir=infra test`: mocked providers, `command = plan`. `tests/stack.tftest.hcl` pins the cross-account grants statement by statement, the Lambda's bounds, the CSP's strictness, the `/api/*` behaviour, the API's origin access control (`AWS_IAM` URL, `lambda` OAC on the origin, both invoke permissions scoped to the distribution, the shared-secret header kept) and the WAF scope. `tests/auth.tftest.hcl` (#28) pins the region refusal, the user table's PITR / TTL / deletion protection, the table, SES and queue grants action by action and ARN by ARN, and that no Lambda policy holds `DeleteSuppressedDestination`. Mocks are per resource type, so `override_resource` gives each queue, topic and key its own value: the tests catch a grant, queue policy, subscription, redrive or event source mapping pointed at the DLQ or the alert topic. Also the queue's visibility timeout, the sign-in mail queue (its DLQ and redrive, retention against the code's life and the retries, the TLS-only policy, the four-action grant, the mapping and the `MAIL_QUEUE_URL` it dispatches on), the reserved-concurrency floor above both mappings, and the sign-in environment wired key by key to its own `random_password` (a structural check: the backend refuses equal keys at start-up). Then `/api/*` uncached with cookies and `Origin` forwarded; the auth WAF rule (STARTS_WITH `/api/auth/`, `/api/auth/me` excluded, `NORMALIZE_PATH_WIN`, per IP over 5 minutes, block), sampled requests off, the WAF alarms' metric-name dimensions, and the log-line alarms. `tests/stack.tftest.hcl` also pins the Lambda's memory and concurrency bounds (2 048 MB, 10 copies, 10 GB in all), the deploy policy action by action (no `GetFunction`), the site bucket's public-access block and policy (CloudFront `GetObject` on this distribution only, the TLS deny), `PriceClass_200` and `TLSv1.2_2021`; `tests/auth.tftest.hcl` the bounce queue's TLS deny and the usage-table grant (`UpdateItem` on that table only). `tests/cost.tftest.hcl` pins the spend guardrails: the CloudFront requests and bytes, Lambda invocations and Route 53 query alarms (5-minute sums at a twelfth of their per-hour variables, each to its region's topic), the breaker (its role's one permission on the API function and own logs, topic → function wiring and the invoke permission, both trips to `alerts` and the breaker topic, their thresholds and the validations that bound them, the API function owning its reserved concurrency), the usage table's contract and caps, the budget's gross cost and its 80 % / 100 % lines, the refusal of `budget_monthly_usd = 0` without `no_budget_acknowledged`, `alert_email` refused when empty or on a reserved example domain, the user table's throughput ceiling, `CFM_TOKEN` wired from `cfm_token`, the Lambda's JSON logging levels, and `DATA_REGION` following `icwbt_region` rather than `aws_region`.
- `node --test infra/scripts/*.test.mjs`: the CSP guard (`scripts/check-csp.mjs`, which `deploy-frontend.yml` runs on every build), the two CloudFront functions, and the breaker function (`breaker.test.mjs`, with a fake `PutFunctionConcurrency`).

Never `terraform apply` from a Claude session, nor a plan against the real backend: those are the operator's (`docs/deployment.md`).

## Cost

Checked 2026-11-07 in the pre-first-deploy cost audit, with published prices from the AWS Price List API: af-south-1 Lambda arm64 $0.00001768 per GB-second and $0.27 per million requests; DynamoDB on-demand $0.84 per million write and $0.168 per million read units; CloudWatch Logs $0.678 per GB ingested; SQS $0.476 per million; SES $0.0001 a recipient; CloudFront at South African and Indian edges $1.20 per million HTTPS requests and $0.110 a GB, WAF $0.60 and CloudFront Functions $0.10 per million; Route 53 $0.40 per million queries. A month is 2 592 000 s.

**Fixed, every month: about $12.70** (about $14.60 with 15 % VAT if billed in South Africa): WAF $5 + 3 rules × $1 = $8, the Route 53 zone $0.50, the bootstrap's sops KMS key $1, and about 42 alarm metrics less CloudWatch's 10 free = $3.20 (the sign-in mail queue added four, issue #30; the breaker's three, the Route 53 alarm and the usage table's one more). The breaker's topic and function cost nothing until they run. The two queues' event source mappings long-poll SQS even when idle (Lambda keeps several pollers on each, every one a 20-second receive): roughly 1.3 million empty receives a month between them, the new mail queue half of that, against SQS's free million requests a month, so a few tens of cents at most. The budget's early line is 80 % of $25 for that reason: at 50 % it would fire every month.

**Worst cases.** "Hard cap" is everything at its cap for a whole month, with nothing stopping it; "under the alarms" is the most that runs all month without a trip or a mail.

So with the breaker the Lambda line, the only one that was over $100 on its own, is stopped automatically, and everything that runs silently under the alarms is about **$107 + $107 at the edge (≈ $15 net of the free tier) + $6 of DNS**. What still has no automatic stop: a flood of fast requests (each is cheap, so it never trips the Duration breaker; the edge, Lambda-request and log lines add up to about $640 a month at Lambda's 100 a second, mailed within 5 minutes), and the edge and DNS lines themselves. The budget lags (actual by up to a day; forecasted needs some spend history, so it is quiet in the first weeks), which is why the CloudWatch alarms and the breaker are the fast layer. The manual kill switches are in `docs/security.md` § Incident playbook.

A durable option for the unbounded edge and DNS lines, not taken (the operator's decision, R4-I10): CloudFront's flat-rate Pro plan ($15 a month, no overage, WAF and the Route 53 zone included) would make them a fixed cost and replace most of the $8.50 of WAF and zone; it doesn't allow custom response-headers policies (Pitman has two), and whether it accepts a Lambda Function URL origin with a `lambda` OAC needs checking first.

## Notes

- **Provider: hashicorp/aws 6.x** (`~> 6.70`, locked 6.71.0, Dependabot #2). The 5 → 6 upgrade needed no resource changes here; v6's per-resource `region` argument isn't used (the `us_east_1` alias stays, as in IC-WBT).
- **Function URL permissions**: the URL is `AWS_IAM`, and the only grants are CloudFront's two statements in `s3_cloudfront.tf` (`AllowCloudFrontServicePrincipal`, `AllowCloudFrontServicePrincipalInvokeFunction`), as AWS's CloudFront guide gives them. The provider (since 6.28) adds its own public-invoke statements only when it creates a `NONE` URL, and removes none when the type changes in place; a stack once applied on `NONE` keeps them until they are removed by hand (`docs/deployment.md` § Lambda origin access control). Never declare a public `aws_lambda_permission`.
- **Secrets** in state: `random_password.cloudfront_shared_secret`, `auth_code_key` and `auth_session_key`; rotation in `docs/deployment.md` § Secrets.
- **The user table can't be destroyed by Terraform**: deletion protection is on, so `destroy` (or a change that forces replacement) fails on it until it is turned off by hand.
- **The deploy role needs nothing new for sign-in**: the table, SES and the queues are Terraform's; the deploy only replaces the function's code (`oidc.tf`).
- **Saved plans hold the secrets.** A `terraform plan -out=tfplan` file carries the three `random_password` results in plaintext. `tfplan` and `*.tfplan` are gitignored, and every plan-and-apply in `docs/deployment.md` ends with `rm infra/tfplan`.
- **Tearing down**: `AWS_PROFILE=pitman terraform -chdir=infra destroy`. The tfstate bucket and the zone belong to the bootstrap and survive.
