# Solving a network

This page specifies how Pitman solves a whole WRSM2000 network: the module
list and its order, routes, what each module type puts on its routes, the
checks made before a run, and what the three run modes (D1) change. It is
the spec for `packages/wrsm/src/network/` (`runNetwork`, `validateNetwork`,
`applyRunMode`). The module simulators themselves are specified elsewhere:
runoff in `pitman.md` (and `sami.md`, `hughes.md`), reservoirs and channels
by their Round 3 agents against `src/network/contract.ts`, and irrigation in
`irrigation.md`.

Sources, all public WRC reports (issue #3 rule 1):

- **TT 689/16**, the User Manual: Introduction pp.xv–xviii (routes, zero
  modules, module roles); §2.2 pp.4–5 (routes, Table 2.1); §6.1.8.1 pp.42–43
  (runoff inflows); §6.1.16 pp.56–58 (running, connectivity, sequence errors,
  Solve); the worked sequence errors on pp.83–84, 92 and 104; SFR children
  pp.133–140; paved areas p.142; diversions pp.147–149; naturalised flows
  pp.13, 27; summary files §4.3 p.13.
- **TT 691/16**, the Programmer's Code Manual: §7.3 The Route Class
  pp.29–31; §12.6 the network file pp.182–184.

File layouts are in `docs/formats.md` §4 (`.NET`) and §5 (RU L.019–L.021);
this page talks about the typed model (`Network`, `Route`, `RunoffModule`, …
in `packages/wrsm/src/types.ts`). Provisional choices carry an ID `R3-N…`
and are listed at the end.

## 1. The module list

`.NET` L.008 lists every module once, as `<number><type><Y|N>`, "in the
order in which you want to solve the network" (TT 691 §12.6 p.183). The
list does three things:

1. **It is the solution order.** "The main function of the network is to
   specify the order in which the modules must be solved" (TT 689 p.xviii).
   Pitman solves modules in exactly this order (R3-N3). The one exception
   is R7-I2: a supplier moves ahead of a module that takes its block's return
   flow, which only arises under R3-N22.
2. **It defines the positions routes refer to.** A route's source and sink
   are "the source (or tail) module number as it appears in the list of
   linetype 8's" (TT 691 p.183), i.e. 1-based positions, not module numbers
   (decisions.md, "Routes"). Module numbers are unique only within a type
   (TT 689 §2.3.1), so `RU 4` and `CR 4` can both appear.
3. **It says which modules are solved.** `Y` solves the module; `N` means
   "the module will not be processed. In this way, a network may be
   shortened somewhat. However, if a module expects inflow generated by an
   upstream module which was not solved, the program will alert the user and
   stop" (TT 691 p.183). TT 689 p.58 repeats it: "if you exclude a module
   from being solved, all downstream modules must also remain unsolved",
   with the example that leaving RU1 unsolved but CR1 solved gives a
   sequence error, and the reverse runs.

Each entry's file is `<net><type><number>.DAT` (TT 689 §2.3.1 p.6). A
`NetworkBundle` holds one module object per entry; `placeModules` matches
them by type and number.

## 2. Routes

A route is "a lossless, dimensionless entity where water flows unimpeded and
without any time delay from one module into the next"; it has no
abstractions, inflows or losses of its own (TT 691 §7.3 p.30; TT 689 §2.2
p.4). Each has a source (upstream, tail) and a sink (downstream, head)
module.

- **Route numbers** run 1–9999 and are unique in a network; they are
  independent of module numbers (TT 689 p.5).
- **The zero module.** Position `0` is "a module which is external to the
  network": a *zero source* brings flow in, a *zero sink* takes it out (TT
  689 §2.2 p.4, p.xv). "Flows along routes that originate in zero source
  modules must be defined by means of a file of monthly values. Routes that
  terminate in a zero sink module may be defined by means of a file of
  monthly flows or may be left undefined if this route is the principal
  outflow route of the network" (p.xv).
- **One flow series per route.** The route record keeps one defined-flow
  file name (`RTFile`, with `IDR` = 1 "if flow defined") and one array of
  flows over the whole simulation, `QRT(MNTPS)` (TT 691 §7.3.1 pp.30–31).
  `RunResult.routeFlows` is that array, one `MonthlySeries` per route, in
  million m³ per month.
- **Both ends name the route.** "The number of a given route will be used
  in both the upstream and downstream modules as well. In the upstream module
  to a route, the route will be defined as an outflow route and in the
  downstream module the route will be defined as an inflow route" (TT 691
  §7.3 p.29). So every route between two modules appears in the `.NET` *and*
  in both module files; the connectivity check (§5) holds them to each
  other.

### 2.1 Which routes each module type names

| Module | Inflow routes | Outflow routes | Defined-flow files |
|---|---|---|---|
| RU (TT 691 §12.1) | L.021 v1 RTIN, at most one (0 = none) | L.020, up to 10, each with a % | none |
| RV (§12.3) | L.011, up to 5 | L.009 spill route (one of the L.013 outflows, TT 689 pp.88–89), L.013, up to 5 | per route line; `'*'` on an outflow = monthly defined abstraction (L.014) |
| CR (§12.2) | L.008, up to 10; L.014 local wetland inflow (one of them) | L.006 principal outflow, L.010, up to 10; L.015 local wetland outflow; L.016 diversion | per route line |
| RR (§12.4) | L.011 abstraction route (exactly one) | L.012 return-flow route (0 = none) | none |
| MM (§12.5) | none | up to 60 | not read (no layout support) |

Route limits are TT 689 Table 2.1 (p.5). Exceeding one is a warning, as in
`docs/formats.md` §4.

### 2.2 Runoff modules: the % split, RTIN and upstream groundwater

- **Outflow split (L.019–L.020).** The module "has the facility to send
  fixed proportions of the total runoff along various routes" (TT 689
  p.xvi (c)). Each L.020 line is a route and the percentage of the total sent
  down it. The percentages must total 100: a run where "the distribution of
  the result flows is not 100% of all flows" is a connectivity error, since
  "flows would either be created or destroyed" (TT 689 p.56). Route flow =
  total × percent / 100, with the percentages as written (R3-N5).
- **Upstream inflow RTIN (L.021 v1).** "Any route from upstream can be made
  an inflow route to a Runoff Module. The outflow from one catchment (or part
  of it) can therefore be routed through the next catchment" (TT 689 p.42).
  With classic Pitman or Sami groundwater "there are no losses – what comes
  in via the inflow route goes out via the outflow route(s). Any runoff that
  is generated by a Runoff Module is added to the inflow" (p.43). So the
  module's total is *generated runoff + RTIN flow*, and the total is what the
  L.020 percentages split (R3-N8). With Hughes groundwater some inflow may be
  lost to the riparian zone, up to TLGMax (p.43); that is Round 6
  (`hughes.md`), and a Hughes module can't run yet (R2-2). TT 689 Table 2.1
  marks the runoff inflow "Hughes groundwater model only", but p.42 allows it
  for every model; Pitman follows p.42. (This answers `subdivide.md` B1: a
  route may end at a runoff module.)
- **Upstream groundwater module (L.021 v2).** A Hughes module may take "the
  final groundwater state" of one other runoff module, which must itself be
  Hughes; "the order in which the modules are solved is important" (TT 689
  p.41). It "has nothing to do with" the inflow route (p.43). Pitman treats it
  as an ordering constraint (§4) and checks that the module exists; the state
  transfer itself is Round 6.
- **`RunResult.runoff`** holds each solved runoff module's diagnostics as
  `runRunoffModule` returns them: *generated* runoff (`netRunoff`), without
  the RTIN inflow.

### 2.3 SFR parents and children

A parent lists its children (L.038–L.039). Each child must have one outflow
route carrying 100 % to a zero module, "or the flows will be counted twice"
(TT 689 p.133, rules A–C); "the Parent Module will 'know' which of the modules
are its Children and will automatically incorporate these outflows into its
own final outflow". "When a Parent Module is run, it first instructs all of
its Child Modules to run their simulation. The position of the Child Module
in the Network is therefore immaterial" (p.135). Child areas are taken out of
the parent month by month (p.135).

None of this is modelled before Round 6 (`runRunoffModule` warns and ignores
SFR children). Until then each child runs as a free module, its outflow
going to the zero sink, and the parent runs on its full area (R3-N11).
Validation checks that every child exists, warns when a child is claimed by
two parents, and warns when a child breaks rules A–C.

### 2.4 Reservoirs, channels and irrigation

These modules name their routes by route number in their own files (table
above). A route line with a defined-flow file carries that file's flows:

- On an **inflow** with a zero source, the file *is* the flow (p.xv).
- On an **outflow** (a demand or abstraction), the file is what the module
  must try to supply; the supply may fall short (TT 689 ch.8).
- An RV outflow defined by file may run into another module rather than a
  zero sink (p.xv). The downstream module may name the route with the same
  file, and then reads the file itself.

An **irrigation abstraction route** carries two streams: "During the
simulation of an Irrigation Module, the flows that are demanded by the crops
in the irrigation module are placed in the 'demand' stream of the Irrigation
Abstraction Route … the Irrigation Module assumes that these demands will be
supplied somehow" (TT 689 p.84); the supplying channel or reservoir then
puts the supply on the route. The route record flags this (`IIR`, "the
irrigation block will set the demands", TT 691 §7.3.1 p.31). So the
irrigation module is solved **before** its supplier, against the route's
direction (§4). "Return Flow Routes may only be connected to Zero Sink
Modules or to modules that are downstream of the module that supplies an
Irrigation Block" (TT 689 p.85); returning to the supplier "has all the
makings of a circular argument" (p.104). A return into the supplier is an
error, and a return that flows back to the supplier shows up as a cycle
(§4). A return into a module that is merely listed earlier, on another
branch, is accepted (R3-N22); the supplier is then solved ahead of that module
(R7-I2).

## 3. Gauges and the summary file

- **Gauges** (L.009–L.011) sit on routes and "are used for comparison only
  whereas defined flows push or pull the flows in the model" (TT 689
  p.xviii). They don't change a run. A gauge on a route the network lacks is
  an error; a missing observed-flow file is a warning (R3-N16).
- **Summary file.** With L.006 = `Y`, WRSM2000 writes `<net>RUN.SUM` (TT 689
  §4.3 p.13), in which "flows in the specified routes or storages in the
  specified reservoirs are stored on a monthly basis" (p.xviii), "one year per
  line" (p.58), for the L.016 elements (`'RT' n 'Q'`, `'RV' n 'Q'`, TT 691
  p.184). Its layout is not documented further and no file has one
  (`docs/formats.md` §11.7). The engine doesn't write it (the CLI would, from
  `routeFlows` and `reservoirStorage`; R3-N15); validation warns when a
  summary line names a route or reservoir the network lacks.

## 4. Solve order and sequence errors

Modules are solved one at a time over the whole record, in list order
(R3-1). The route record's whole-record flow array `QRT(MNTPS)` and its
"flow in route has been calculated" flag `ICR` (TT 691 §7.3.1 p.31) fit this:
a module reads complete series from routes already done.

A **sequence error** "is generated when a particular module expects inflows
from an upstream module but that upstream module has not yet been solved"
(TT 689 p.56); it "can only be solved by rearranging the order in which the
modules are solved". TT 691 p.183: "a runoff submodel should be solved before
the outflow of such a submodel is required by the more downstream module.
The demands of an irrigation block should also be determined before its
source module." The constraints (`networkDependencies`):

| Kind | Rule | Source |
|---|---|---|
| flow | a route's upstream module before its downstream module | TT 689 p.56, pp.92 (RV spill into CR) |
| demand | an irrigation module before the module that supplies its abstraction route | TT 691 p.183; TT 689 pp.83–84 |
| return flow | an irrigation module's supplier "upstream" of the module its return flow enters; used only to find cycles, never as a sequence error | TT 689 p.85; R3-N22 |
| groundwater | a runoff module's upstream groundwater module before it | TT 689 p.41 |
| none | a route the **downstream** module reads from a defined-flow file | R3-N4 |

Every irrigation module in the reference set is listed before its supplier
(297 abstraction routes); two reservoir-to-reservoir routes run against the
list order and both are defined by file at both ends, which is why defined
routes impose no order (R3-N4).

Checked against the `Y`/`N` flags:

- a solved module that depends on an **unsolved** one is a sequence error
  (TT 691 p.183; TT 689 p.58);
- a solved module that depends on one **later** in the list is a sequence
  error, reported with the fix ("move RV 5 above CR 4");
- a constraint whose dependent module is unsolved is ignored.

**Cycles.** "Attempting a circular argument, e.g. by routing the outflows from
the Channel Reach back into the Runoff Module may appear to work at first, but
will be rejected when a connectivity check is made just before the
simulation runs" (TT 689 p.48; also p.104). A loop of constraints (a strongly
connected group of modules) is reported once, naming every module and route
in it, instead of as sequence errors, since no order solves it.

## 5. Validation (`validateNetwork`)

"Two operations are carried out before the simulation is run; the data in
each of the modules in the Network is checked and the connectivity of the
modules in the Network is checked. If there are data errors in the modules,
or there are connectivity errors in the network, error messages will show you
where those errors are and the simulation will halt" (TT 689 p.56). Pitman
reports **every** problem at once as `RunMessage`s naming the module (type,
number, file), the route and the file; `runNetwork` throws one
`NetworkError` carrying them all if any is an error.

| Check | Level |
|---|---|
| a module-list entry with no file in the bundle; an entry listed twice | error |
| a route number used twice; an endpoint outside 0…M; a route from zero to zero; a route that starts and ends in one module (TT 689 p.48) | error |
| a module file names a route the `.NET` lacks, or names it as an outflow (inflow) while the `.NET` routes it from (to) another module | error |
| a `.NET` route leaving (entering) a module whose file doesn't name it as an outflow (inflow) | error |
| a route from the zero module whose downstream module gives it no defined-flow file (p.xv) | error (warning when that module is unparsed) |
| a defined-flow file, RU, RV or RR rainfall file, or CR wetland rainfall file (wetland type ≠ 0) that the bundle lacks | error |
| an RU module with no outflow routes (TT 689 p.133), the same L.020 route listed twice, or percentages missing 100 by more than 0.05 % per route (R3-N5) | error |
| an irrigation return flow into the module that supplies it (TT 689 p.85, p.104) | error |
| a missing upstream groundwater module or SFR child | error |
| sequence errors and cycles (§4) | error |
| a gauge on a route the network lacks | error |
| the two ends of a route naming different defined-flow files (one `RTFile` per route) | warning (R3-N18) |
| an SFR child claimed twice, or breaking TT 689 p.133 rules A–C | warning |
| more routes than TT 689 Table 2.1 allows | warning |
| a missing observed-flow file; a summary line naming a missing route or reservoir | warning |

At run time (`runNetwork`) a module also warns, in historical mode, when its
paved-area years don't cover the run: "the Paved Area year/area data must
cover the entire simulation period. If this is not the case, the module will
issue a warning" (TT 689 p.142). It is held flat beyond them (OQ-17).

## 6. Running (`runNetwork`)

1. Validate (§5); throw `NetworkError` on any error.
2. Put each zero-source route's defined flow on it: `definedFlowSeries` of
   the file its downstream module names, in the run mode (R3-2).
3. For each module in list order:
   - **not solved (`N`)**: its outflow routes carry zero; an info message
     (R3-N12).
   - **RU**: `runRunoffModule(applyRunMode(module, mode), rainfall, …)`.
     Total = generated runoff + RTIN flow; each L.020 route gets its share
     (§2.2). A Sami or Hughes module makes `runRunoffModule` throw a
     `PitmanRunError` naming it, and the run fails (R2-2).
   - **RV, CR**: the simulator gets, as `inflows`, the flow on every inflow
     route that has an upstream module and no defined-flow file; a defined
     route it reads itself through `ctx.flowFile` (`contract.ts`). As
     `demands` it gets the demand of each irrigation module drawing on it. Its
     outflows go on the routes that leave it in the `.NET`. A route it leaves
     out carries zero (warned), a route it returns that isn't its own is
     ignored (warned) (R3-N13), and a series of the wrong length fails the
     run. RV storage goes to `reservoirStorage[number]`. A simulator's error
     is rethrown as a `NetworkError` naming the module (cause kept).
   - **RR**: two passes (`irrigation.md` §2, R7-I2). At its place in the list
     it computes its demand and puts it on the route's demand stream. As soon
     as the abstraction route has a flow, normally right after the supplier,
     it settles against that flow and puts its return on the return route. In
     natural mode it is removed: an info message, zero on both routes.
   - **unparsed** (a mine, or an unknown file version): zero on every route
     that leaves it, with a warning naming it and the reader's reason
     (R3-N7).
4. Every `.NET` route gets a series (zeros for any route nothing set), each
   `12 × (endYear − startYear + 1)` months from `startYear`.

Messages are collected in order: validation warnings, then each module's in
solve order.

### 6.1 Network water balance (the invariant)

Over every month, with pass-through simulators that report their losses:

    Σ runoff generated + Σ zero-source (defined) inflows
      + Σ irrigation return flows
      = Σ flow on routes into the zero sink or into a module that consumes it (RR, MM, unparsed, unsolved)
      + Σ reservoir storage change + Σ simulator losses

Inside an irrigation module the balance closes on its own terms (`irrigation.md`
§10).

Routes are lossless (§2), so the balance closes to rounding error.
`run-network.test.ts` checks it in all three modes on `syntheticBundle()`.

## 7. Run modes (D1)

| Module | historical | present day (year Y) | natural |
|---|---|---|---|
| RU | as the file says | afforestation, alien vegetation and paved year tables, and Sami groundwater abstractions (L.036–L.037), held at their value in Y (interpolated, flat beyond the table; R3-N10) | paved area, afforestation, alien vegetation removed (TT 689 p.27), so SFR children have no effect (p.13); groundwater abstractions removed (R3-N9) |
| RV | simulator (`ctx.mode`) | simulator: capacity and drafts at Y | simulator: the dam removed, inflow passes to the spill route, drafts zero (`contract.ts`) |
| CR | simulator | simulator | simulator (defined abstractions zero) |
| RR | area, allocation, efficiency, return and capacity tables by year | held at Y | removed (`irrigation.md` §3) |
| MM, unparsed | zero (R3-N7) | zero | zero |
| defined-flow files | each year's row (R3-2) | the row for Y, else the nearest year (R3-2) | zero (R3-2) |

`applyRunMode(module, mode)` is pure and returns the runoff module as the
mode sees it, for running only (a held table has one year). Present day
follows the procedure TT 689 p.138 gives for WRYM input: "change the areas of
alien veg so that the start year and end year are for the current area".
Natural follows the per-module "Simulate Naturalised outflows" box: "the
module will ignore all man-made module data such as Paved areas,
Afforestation and Alien Vegetation and so produce naturalised outflows" (TT
689 p.27). D1's natural mode also removes irrigation, dams and abstractions,
which the simulators and `definedFlowSeries` do.

## 8. The reference set (local only)

`network-connectivity.reference.test.ts` validates every `.NET` under
`WRSM_REFERENCE_DIR` (skipped when unset). On 2026-10-29: **35 networks, 34
valid, 1 with one error**, a sequence error: a runoff module (an SFR parent)
is listed one place after the channel it drains into, yet the archive holds
outputs for that network. Either WRSM2000 tolerates this ("the program
retains some of its former intelligence", TT 689 p.57) or the outputs come
from another order (R3-N3). No warnings, no missing files, every module file
read, every RU percentage exactly 100, and every module file agrees with its
`.NET` routes.

## 9. Open questions (with proposed defaults)

- **R3-N1** Whole-record, one module at a time (R3-1). Supported by TT 691
  §7.3.1 (`QRT(MNTPS)`, `ICR`). But TT 689 p.149, on a channel diverting
  into a reservoir: "a Reservoir can only be solved once all of the inflows
  and demands on it are known … we can only ask the reservoir to supply the
  spare capacity for the end of the previous month, since the reservoir
  itself has not been solved for the month". That needs month-by-month
  interleaving, or the reservoir's storage before the channel is solved.
  Default: whole record; a diversion into a reservoir has no spare-capacity
  demand until the contract can carry it. No reference channel has a
  diversion route.
- **R3-N2** The irrigation demand stream (§2.4): a channel or reservoir
  supplying an irrigation module needs that module's demand, and TT 689 p.148
  says that "when the supply is less than the demand, the Irrigation Module
  is told to adjust" (feedback). `ModuleSimulators` gets no demands. Default:
  no demand until Round 7; the contract needs a `demands` argument (route →
  series) before then. **Closed by R7-I2:** the argument exists; demand doesn't
  depend on supply, so the feedback needs no iteration.
- **R3-N3** Sequence errors are errors, as TT 689 p.56 and TT 691 p.183 say;
  Pitman never reorders. One public reference network then fails (§8).
  Alternative: solve runoff modules first when nothing else depends on them.
  Default strict. R7-I2 adds the one reorder.
- **R3-N4** A route its downstream module reads from a defined-flow file
  imposes no order (the downstream module doesn't wait for the upstream one).
  Needed by two reference routes.
- **R3-N5** RU percentages are used as written, not rescaled. The check
  allows 0.05 % per route (half the `F6.1` resolution), so 3 × 33.3 passes
  and then loses 0.1 % of the module's runoff every month. Every reference
  module sums to exactly 100, so the reference can't tell whether WRSM2000
  rescales; if it does, this is a departure.
- **R3-N6** RR modules before Round 7: zero demand on the abstraction route
  and zero on the return-flow route, with a warning (info in natural mode).
  **Superseded by `irrigation.md`.**
- **R3-N7** MM and unparsed modules: zero on every outflow route, with a
  warning. A mine also generates runoff from its own area, so a network with
  one under-counts flow; none exists in the reference set.
- **R3-N8** RTIN is added to generated runoff before the L.020 split (TT 689
  p.43), for classic and Sami modules; Hughes losses are Round 6.
- **R3-N9** Natural mode also removes Sami groundwater abstractions (L.036–
  L.037) and zeroes the Hughes annual abstractions (L.027, L.029). TT 689
  p.27 names only paved area, afforestation and alien vegetation; D1 adds
  "abstractions". Sami abstraction mode 2 (a time-series file, TT 691
  §11.21) isn't read yet and so isn't covered.
- **R3-N10** Present day holds every RU year table at its linearly
  interpolated value in the chosen year, flat beyond the table's last year
  (no extrapolation), the OQ-17 rule. Round 7 extends the tables to 2025.
- **R3-N11** SFR children run as free modules (to the zero sink) and parents
  on their full area until Round 6; child positions aren't special-cased.
  Superseded by the SFR group run in `docs/theory/afforestation.md`
  (`runSfrGroup`) once it is wired into the runner (Round 6 integration).
- **R3-N12** An unsolved module puts zero on its routes and has no
  diagnostics; the manual says only that it "will not be processed".
- **R3-N13** A simulator that leaves out one of its routes gets zero there
  (warned); a route it returns that isn't its own is ignored (warned).
- **R3-N14** A zero-source route's series in `routeFlows` is
  `definedFlowSeries` in the run mode, which simulators are expected to use
  for the same file. A simulator result field naming the inflow series it
  used would remove the duplication.
- **R3-N15** The engine doesn't write `.SUM`; the layout is undocumented
  beyond "one year per line". Summary-line references are only checked.
- **R3-N16** A missing observed-flow file is a warning: gauges don't affect a
  run.
- **R3-N17** Exceeding TT 689 Table 2.1 is a warning, as `formats.md` §4.
- **R3-N18** When both ends of a route name a defined-flow file and they
  differ, the downstream module's file is read (warned); TT 691 §7.3.1 keeps
  one `RTFile` per route.
- **R3-N19** `RunResult` has no slot for channel (wetland) storage; a
  channel simulator's `storage` is checked and dropped.
- **R3-N21** A solved channel or reservoir that supplies an **unsolved**
  irrigation module is a sequence error (it would wait for a demand nobody
  sets). TT 689 p.58 only says modules *downstream* of an unsolved one must be
  unsolved, and the supplier is upstream, so WRSM2000 may accept this. No
  reference network has an unsolved module.
- **R3-N22** TT 689 p.85's "downstream of the supplier" is enforced only as
  "no loop back to the supplier", not as list order: one public reference
  network returns irrigation flow into a channel listed before the supplying
  reservoir, on a branch the reservoir doesn't drain into, and was run.
- **R3-N20** The paved-coverage warning (TT 689 p.142) is given only in
  historical mode; the other modes don't read the table year by year.
